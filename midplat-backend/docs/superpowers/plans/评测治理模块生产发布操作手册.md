# 评测治理模块生产发布操作手册

> **供执行人员使用：** 本手册是评测治理模块从代码候选版本进入预生产、正式生产和发布后观察的逐步操作清单。涉及代码整改时，执行人员必须使用测试驱动方式完成，并在每个任务结束后进行独立复核。

**目标：** 在不泄漏凭据、不破坏现有数据库、不跳过审计和回滚准备的前提下，将 AI 中台评测治理 P1–P5 安全发布到生产。

**架构：** 前端以 Nginx 静态站点提供 /evaluation 页面，并通过同源 /api 访问 Spring Boot。后端使用 PostgreSQL、Flyway V1–V26、持久化评测任务和进程内受限执行线程池；模型调用通过中台模型、Prompt 和平台绑定完成。首期门禁只生成决策，不自动执行生产部署，V26 会把菜单标记为“评测治理（开发中）”。

**技术栈：** Java 17、Spring Boot 3.2.5、PostgreSQL、Flyway、React 18、Umi Max、Ant Design、Nginx、Docker、Kubernetes。

**规格：** docs/superpowers/specs/2026-08-29-AI数据飞轮与评测治理模块设计及建设跟踪.md

## 全局约束

- 本手册只发布 P1–P5。P6 知识库、智能体和标注平台连接器不包含在首期生产范围。
- 任何包含未脱敏患者数据、真实 API Key、数据库密码或生产访问令牌的内容不得写入 Git、命令日志、截图和发布证据。
- 数据库生产基线固定为 PostgreSQL，并要求事务隔离级别为 READ COMMITTED。
- Flyway 迁移只允许向前执行。禁止修改已经在任何环境执行过的迁移文件或 checksum。
- 所有镜像使用不可变版本号或 Git SHA，禁止生产部署使用 latest。
- 所有生产发布必须先完成预生产演练、备份恢复演练和回滚演练。
- 所有步骤使用复选框跟踪。某一步的停止条件命中后，不得继续后续步骤。
- 发布操作至少由研发、运维、业务负责人三方共同执行；涉及医疗或患者数据时还需要安全或合规负责人确认。

## 4. 阶段二：完成生产前代码阻塞项

### Task 2：移除并轮换硬编码凭据

**涉及文件：**

- 后端：src/main/resources/application.yml
- 生产：Kubernetes Secret 或公司 Secret Manager

- [ ] **步骤 1：确认仓库存在开发数据库默认值**

运行：

    git grep -nE "password:|api-key:|secret:|token:" -- src/main/resources

预期：只允许出现环境变量引用或空默认值。任何真实值都必须整改。

- [ ] **步骤 2：将数据库配置改为环境变量**

application.yml 的 datasource 必须只引用：

    SPRING_DATASOURCE_URL
    SPRING_DATASOURCE_USERNAME
    SPRING_DATASOURCE_PASSWORD

禁止保留可直接连接任何共享数据库的默认密码。

- [ ] **步骤 3：轮换仓库中曾出现过的数据库密码**

操作顺序：

1. DBA 新建或轮换专用 midplat 应用账户。
2. 只授予目标 schema 必需的连接、DML 和 Flyway 迁移权限。
3. 将新密码写入 Secret Manager。
4. 验证新账户可连接。
5. 吊销旧密码。
6. 在发布证据中只记录轮换完成，不记录密码正文。

停止条件：旧凭据仍然有效或新账户权限大于应用需要时停止。

- [ ] **步骤 4：执行秘密扫描**

使用公司批准的秘密扫描工具扫描：

    git log --all --oneline
    git grep -nE "(password|api[_-]?key|secret|token)"

将扫描报告放入 03-安全与权限。发现真实凭据时先轮换，再处理历史。

### Task 3：接入认证、RBAC 和真实操作者审计

**当前事实：** 后端未引入 Spring Security，评测审计 actor_ref 当前记录为 system。

- [ ] **步骤 1：确定生产角色矩阵**

最小角色必须包含：

| 角色 | 允许操作 |
| --- | --- |
| EVALUATION_VIEWER | 总览、案例摘要、数据集、运行、比较、门禁历史只读 |
| EVALUATION_EDITOR | 创建和编辑草稿案例、创建数据集草稿 |
| EVALUATION_REVIEWER | 审核/驳回案例、人工评分、冻结数据集 |
| EVALUATION_ADMIN | 门禁策略、门禁决策、取消/重试任务、归档 |

同一个账号不应默认同时拥有创建和审核高风险案例的权限。

- [ ] **步骤 2：为所有 /api/evaluation/** 接口编写权限测试**

必须覆盖：

1. 未登录返回 401。
2. 已登录但无权限返回 403。
3. VIEWER 不能执行写操作。
4. EDITOR 不能审核和冻结。
5. REVIEWER 可以审核、冻结和人工复核。
6. ADMIN 可以管理策略和门禁。

- [ ] **步骤 3：接入公司统一身份**

要求：

- 使用公司现有 SSO、JWT 或网关身份，不自建用户名密码。
- 后端只信任经过签名验证或受信网关注入的身份。
- 前端只用于交互提示，最终权限必须由后端强制。

- [ ] **步骤 4：把真实身份写入审计**

将 EvaluationAuditService 中固定的 system 替换为可信 principal 的稳定用户标识。不得把姓名、邮箱、JWT 或完整请求头写入审计摘要。

- [ ] **步骤 5：执行权限回归**

运行新增权限测试和后端全量：

    mvn clean test

停止条件：存在任何评测写接口无鉴权，或审计无法关联真实操作者时停止。

### Task 4：收紧网络暴露面

- [ ] **步骤 1：收紧 CORS**

修改 WebConfig，使 allowedOrigins 只接受生产前端域名和审批的预生产域名。禁止生产使用星号。

- [ ] **步骤 2：保护 Swagger**

生产环境采用以下任一方案：

1. 完全关闭 Swagger UI 和 OpenAPI 文档。
2. 仅允许管理网络访问，并要求管理员身份。

- [ ] **步骤 3：保护 Actuator**

只暴露 health 和 info 到集群内部。Prometheus 指标若启用，也只允许监控系统访问。

- [ ] **步骤 4：配置 TLS**

生产入口必须使用 HTTPS。Ingress 到 Provider 的出站连接也必须验证合法证书，不允许跳过证书校验。

### Task 5：升级并验证 Flyway

- [ ] **步骤 1：记录当前 Flyway 版本**

运行：

    mvn dependency:tree -Dincludes=org.flywaydb:flyway-core

- [ ] **步骤 2：选择公司依赖治理批准且支持 PostgreSQL 16 的 Flyway 版本**

版本由依赖治理或架构负责人批准。不要直接追随未验证的最新版本。

- [ ] **步骤 3：升级后执行迁移回归**

运行：

    mvn clean test
    mvn -Dmidplat.postgres.url=jdbc:postgresql://localhost:5432/postgres -Dtest='*LocalPostgresTest' test

预期：

- 后端全量 0 失败、0 错误。
- PostgreSQL 专项至少 45 项执行，全部通过。
- 随机测试 schema 残留为 0。
- 不再出现 PostgreSQL 16 未受支持告警。

- [ ] **步骤 4：核对 V23 历史**

在每个已部署环境运行：

    select version, description, checksum, success
    from flyway_schema_history
    where version in ('23', '24', '25')
    order by installed_rank;

如果任何环境已经执行过与当前仓库 checksum 不同的 V23，禁止覆盖 V23；必须新增后续迁移进行修正。

### Task 6：补齐生产监控

- [ ] **步骤 1：增加最小评测指标**

至少采集：

- evaluation_queue_depth
- evaluation_runs_total，按状态区分
- evaluation_run_duration_seconds
- evaluation_case_execution_errors_total
- evaluation_provider_requests_total，按 HTTP 状态区分
- evaluation_provider_latency_seconds
- evaluation_tokens_total，按模型和输入/输出区分
- evaluation_cost_total，按模型和平台区分
- evaluation_recovery_actions_total
- evaluation_gate_decisions_total，按结论区分

- [ ] **步骤 2：增加告警**

首期默认告警基线：

| 告警 | 触发条件 |
| --- | --- |
| 队列积压 | queue depth 连续 10 分钟大于容量的 80% |
| 运行失败 | 15 分钟失败率大于 5% |
| Provider 异常 | 5 分钟 429/5xx 大于 1% |
| 运行卡死 | RUNNING 超过 lease 时间仍无 heartbeat |
| 成本突增 | 当日成本超过业务批准预算的 80% |
| 人工积压 | 待人工复核数量超过业务规定阈值 |
| 恢复异常 | recovery failed 日志出现一次即告警 |

业务或 SRE 调整阈值时，必须在发布工单记录最终值。

- [ ] **步骤 3：建立仪表盘**

仪表盘至少展示：

- 队列、运行中、成功、部分失败和失败数量。
- P50/P95 Provider 延迟。
- Token 与成本趋势。
- 429/5xx。
- 人工待复核数量和最长等待时间。
- 门禁 PASS/FAIL/REVIEW_REQUIRED。

### Task 7：增加紧急关闭能力

- [ ] **步骤 1：增加评测模块开关**

生产应具备关闭以下能力的配置：

- 禁止创建新评测任务。
- 禁止生成新门禁决策。
- 隐藏或禁用评测治理菜单。
- 保持历史数据只读可查询。

- [ ] **步骤 2：验证关闭行为**

关闭后必须满足：

- 新建运行返回明确的服务不可用响应。
- 已完成历史仍可读取。
- 数据库迁移和审计数据不被删除。
- 恢复开关后不重复执行已完成任务。

## 6. 阶段四：数据库备份、恢复与迁移演练

### Task 10：生产备份前置检查

- [ ] **步骤 1：由 DBA 确认数据库信息**

确认：

- PostgreSQL 主版本。
- 数据库名称与 schema。
- 当前连接数、容量、磁盘余量。
- 备份保留位置和加密方式。
- 恢复所需时间。

- [ ] **步骤 2：执行一致性备份**

示例命令由 DBA 在受控终端执行：

    pg_dump --format=custom --no-owner --no-acl --file=ai_midplat_before_evaluation.dump DATABASE_NAME

DATABASE_NAME 必须从生产变更单复制，不允许凭经验输入。

- [ ] **步骤 3：记录备份校验**

运行：

    pg_restore --list ai_midplat_before_evaluation.dump
    shasum -a 256 ai_midplat_before_evaluation.dump

把摘要、大小、时间和保存位置写入 02-数据库备份与迁移。

### Task 11：在恢复副本执行迁移

- [ ] **步骤 1：创建隔离恢复库**

恢复库不得与生产数据库同名，不得允许生产应用连接。

- [ ] **步骤 2：恢复备份**

    createdb RESTORE_DATABASE_NAME
    pg_restore --no-owner --no-acl --dbname=RESTORE_DATABASE_NAME ai_midplat_before_evaluation.dump

- [ ] **步骤 3：对恢复库启动候选后端**

使用候选 JAR、恢复库 URL 和隔离端口启动一次，让 Flyway 执行 V1–V26。

- [ ] **步骤 4：核对迁移**

运行：

    select version, description, success
    from flyway_schema_history
    order by installed_rank;

    select count(*)
    from information_schema.tables
    where table_schema = 'TARGET_SCHEMA'
      and table_name like 'midplat_eval_%';

预期：

- Flyway 到 V26。
- 所有迁移 success=true。
- 评测表、约束、索引和外键存在。
- 既有中台数据条数未异常变化。

## 20. 快速停止条件汇总

以下情况不要继续发布：

1. Git 工作树不干净或发布提交未审查。
2. 任一自动化测试失败。
3. TypeScript 或生产构建失败。
4. PostgreSQL 专项失败或临时 schema 有残留。
5. 生产凭据仍存在于代码库。
6. 评测写接口无认证或无 RBAC。
7. CORS、Swagger、Actuator 暴露不符合生产要求。
8. 真实 Provider 未通过成功、限流、错误、超时和费用验收。
9. 备份无法恢复。
10. Flyway checksum 不一致。
11. 监控和回滚未演练。
12. 生产数据未明确脱敏与保留政策。
13. Critical/High 安全问题未清零或无有效豁免。
14. 业务负责人未批准冻结数据集和门禁策略。

只有全部停止条件解除，才能进入正式生产发布。
