## 2. 背景与实际问题

公司现有 AI 能力已经分布在 AI 中台、知识库、数据标注平台、智能体平台、指标 Agent 和闭环平台中：

- AI 中台管理模型、Prompt、平台绑定和运行配置。
- 知识库保存问答历史、引用和用户反馈。
- 数据标注平台提供人工标注、复核和发布流程。
- 智能体平台保存失败案例、训练材料和版本评测信息。
- 指标 Agent、根因报告等业务应用产生 SQL、工具轨迹和业务验收结果。

当前缺口不是“再增加一个 AI 对话入口”，而是缺少统一机制回答以下问题：

- 新模型、新 Prompt 或新知识库版本是否真的优于旧版本？
- 修复一个案例后，是否破坏了其他原本正确的案例？
- 线上失败是否被沉淀为可复用的评测资产？
- 一个版本是否达到明确、可审计的发布标准？
- 模型质量、成本和延迟之间的变化是否可量化？

本模块负责把分散的线上反馈转化为版本化评测集，通过可重复运行的实验和发布门禁形成持续改进闭环。

## 3. 最终实现目标

最终系统必须具备以下能力：

### 3.1 统一案例资产

- 接收人工录入和外部平台导入的失败、成功、边界及安全案例。
- 记录来源平台、业务场景、严重程度、输入、期望结果、实际结果、证据与运行轨迹。
- 对导入事件提供幂等去重和来源追溯。
- 在进入中台前完成患者及业务敏感信息脱敏；中台不保存外部系统原始密钥。

### 3.2 版本化评测数据集

- 将审核通过的案例编入评测数据集。
- 数据集以不可变版本参与评测；已冻结版本不得原地修改。
- 保存版本快照哈希，确保同一实验可重复执行。
- 支持基础集、回归集、高风险安全集和具体业务场景集。

### 3.3 可重复评测执行

- 固定模型、Prompt、数据集和运行参数快照后批量执行案例。
- 首期支持确定性评测：精确匹配、包含断言、JSON 合法性、禁止词、数值区间和人工复核。
- 后续支持经人工校准的 LLM Judge，但 LLM Judge 不得作为高风险案例的唯一裁决者。
- 保存单案例输出、评分、错误、延迟、Token、成本和可脱敏的运行轨迹。

### 3.4 实验对比

- 比较基线运行与候选运行。
- 明确列出改进、持平、退化和执行错误案例。
- 同时展示质量、成本、平均延迟和 P95 延迟变化。
- 支持模型、Prompt、检索配置、Agent 或知识版本的对比语义。

### 3.5 发布门禁

- 按平台和业务场景配置质量、安全、成本和性能阈值。
- 为评测运行生成 `PASS`、`FAIL` 或 `REVIEW_REQUIRED` 门禁结论。
- 高风险安全案例必须全部通过；自动评分不足以裁决时必须进入人工复核。
- 首期只生成发布决策，不自动部署生产；待中台具备正式发布流后再接入硬阻断。

### 3.6 可审计与可运营

- 任何数据集冻结、评测启动、人工改分和门禁决策都要留存操作与时间信息。
- 评测失败允许重试，但历史运行和原始结果不可被覆盖。
- 页面能够展示进行中任务、失败原因、最近趋势和退化案例。

## 4. 非目标

本模块不负责：

- 训练或微调基础大模型。
- 替代数据标注平台的标注工作台和复核流程。
- 替代知识库的文档处理、检索与 RAG。
- 替代智能体平台的 Agent、技能、工具和工作流运行时。
- 自动修改 Prompt、知识库或业务规则后直接上线。
- 在首期自建多租户、企业 RBAC、消息队列或独立计费系统。
- 保存完整 API Key、数据库密码、患者身份原文或未脱敏运行日志。

## 5. 方案比较与最终选择

### 5.1 方案 A：直接并入现有中台模块化单体

核心领域、异步任务和页面全部放在现有前后端仓库。

- 优点：复用模型、Prompt、平台和菜单体系，交付最快，运维成本最低。
- 缺点：评测任务增多后会占用中台进程资源。

### 5.2 方案 B：中台管控面加独立评测 Worker

中台持有领域数据和 API，执行器作为独立进程消费数据库任务。

- 优点：执行与管控隔离，便于横向扩展和限制模型并发。
- 缺点：首期增加部署、版本和故障排查成本。

### 5.3 方案 C：完全独立评测微服务

评测平台拥有自己的前后端和数据库，中台仅提供入口。

- 优点：自治度最高，适合未来单独商品化。
- 缺点：立即产生模型、Prompt、权限和平台档案的重复建设。

### 5.4 决策

采用“方案 A 起步、保留方案 B 的执行端口”：

- 首期作为 AI 中台一级模块落在现有前后端仓库。
- 后端领域包保持独立，通过 `EvaluationTargetExecutor` 接口调用目标系统。
- 评测任务使用持久化状态，不依赖只存在于内存中的队列。
- 首期可在中台进程内由受限线程池执行；未来不修改领域和 API 即可拆出 Worker。
- 不采用完全独立微服务，避免当前阶段重复建设。

## 6. 系统边界

| 系统 | 继续负责 | 与评测模块的契约 |
| --- | --- | --- |
| AI 中台模型与 Prompt | 模型连接、Prompt 内容和平台绑定 | 评测运行只读取并形成不可变快照 |
| 知识库 | RAG、引用、问答历史和反馈 | 输出经脱敏的案例事件；接受指定版本的评测请求 |
| 数据标注平台 | 人工标注、复核、任务分配 | 接收复核任务并回传审核结论 |
| 智能体平台 | Agent、工作流、工具和版本运行 | 输出失败案例；按指定版本执行评测 |
| 指标/闭环平台 | 业务事实、SQL、工具和人工确认 | 输出领域案例与业务证据 |
| 评测治理模块 | 案例、数据集版本、评测编排、对比和门禁 | 不复制上述系统的核心业务能力 |

## 8. 核心数据模型

所有主键沿用中台 `varchar(64)` ID；所有可变聚合包含 `created_at`、`updated_at` 和乐观锁 `version`，不可变审计记录使用独立事件时间。

### 8.1 `midplat_eval_case`

| 字段 | 说明 |
| --- | --- |
| `id` | 案例 ID |
| `platform_id` | 来源或归属平台，可为空 |
| `name` | 案例名称 |
| `category` | 业务分类 |
| `severity` | `LOW/MEDIUM/HIGH/CRITICAL` |
| `source_type` | `MANUAL/KNOWLEDGE/AGENT/INDICATOR/CLOSED_LOOP` |
| `source_ref` | 来源侧脱敏后的唯一引用 |
| `input_text` | 评测输入 |
| `expected_json` | 期望与断言配置 JSON |
| `evaluator_type` | 首期评分器类型 |
| `review_status` | `DRAFT/REVIEWED/REJECTED` |
| `content_hash` | 幂等去重哈希 |
| `lifecycle_status` | `ACTIVE/ARCHIVED`，不物理删除历史案例 |

来源引用非空时以 `(source_type, source_ref)` 保证幂等；内容哈希用于相似案例提示，不强制阻止人工创建业务上不同但内容相同的案例。

### 8.2 `midplat_eval_dataset` 与 `midplat_eval_dataset_version`

数据集保存稳定身份；版本保存版本号、状态、快照哈希和冻结时间。版本状态为 `DRAFT/FROZEN/ARCHIVED`，只有 `DRAFT` 可编辑。

同一数据集的 `version_no` 唯一，版本号只递增、不复用。

### 8.3 `midplat_eval_dataset_item`

绑定数据集版本与案例，并保存顺序；同一版本中一个案例只能出现一次。冻结时校验所有案例均已审核且至少包含一个案例。

### 8.4 `midplat_eval_run`

保存数据集版本、目标类型、目标 ID、模型/Prompt/参数快照、状态、统计、取消标记、开始与结束时间。状态流转：

```text
QUEUED -> RUNNING -> COMPLETED
                  -> PARTIAL
                  -> FAILED
                  -> CANCELLED
```

### 8.5 `midplat_eval_result`

保存单案例实际输出、评分、通过状态、错误码、脱敏轨迹、延迟和用量；同一运行中一个案例只有一条最终结果，重试过程写入结果的 `attempt_count` 和脱敏错误摘要。单结果状态为 `PENDING/RUNNING/PASSED/FAILED/ERROR/CANCELLED`。

### 8.6 `midplat_eval_gate_policy` 与 `midplat_eval_gate_decision`

策略保存平台、适用分类和阈值 JSON；决策保存运行、结论、命中规则和人工复核状态。门禁历史不可覆盖。

### 8.7 `midplat_eval_audit_log`

追加记录模块内写操作的动作、资源类型、资源 ID、来源、操作者引用、发生时间和脱敏摘要。当前中台没有统一登录身份时，操作者引用记录为 `system` 或可信来源平台；接入统一身份后沿用同一字段，不改历史结构。

## 9. 首期 API 契约

统一前缀：`/api/evaluation`。

### 9.1 案例

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/cases?page=0&size=20` | 分页筛选案例，返回不含输入和期望正文的轻量摘要；`size` 上限 100 |
| `POST` | `/cases` | 人工创建案例 |
| `GET` | `/cases/{id}` | 查询案例详情 |
| `PATCH` | `/cases/{id}` | 编辑草稿案例 |
| `POST` | `/cases/{id}/review` | 审核通过或驳回 |
| `POST` | `/cases/{id}/archive` | 逻辑归档案例 |
| `POST` | `/cases/import` | 以来源引用幂等导入案例 |

案例正文与期望 JSON 均限制为 20,000 个字符。`PATCH /cases/{id}`、`POST /cases/{id}/review` 和 `POST /cases/{id}/archive` 的请求体必须携带 `expectedVersion`；版本过期或数据库乐观锁冲突统一返回 HTTP 409，成功响应返回落库后的新版本号。

### 9.2 数据集

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/datasets` | 数据集列表 |
| `POST` | `/datasets` | 创建数据集及首个草稿版本 |
| `POST` | `/datasets/{id}/versions` | 从冻结版本派生新草稿 |
| `PUT` | `/dataset-versions/{id}/items` | 替换草稿版本案例清单 |
| `POST` | `/dataset-versions/{id}/freeze` | 校验并冻结版本 |

### 9.3 评测与对比

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/runs` | 评测任务列表 |
| `POST` | `/runs` | 基于冻结数据集创建任务 |
| `GET` | `/runs/{id}` | 任务摘要 |
| `GET` | `/runs/{id}/results` | 单题结果 |
| `POST` | `/runs/{id}/cancel` | 请求取消 |
| `POST` | `/runs/{id}/retry-errors` | 将执行错误复制为新任务重跑 |
| `GET` | `/experiments/compare` | 对比两个已结束运行 |

### 9.4 门禁

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/gates` | 门禁策略列表 |
| `POST` | `/gates` | 创建策略 |
| `PATCH` | `/gates/{id}` | 更新策略 |
| `GET` | `/gate-decisions?runId=...` | 按运行查询追加式门禁历史 |
| `POST` | `/runs/{id}/gate-decision` | 对运行生成不可变门禁决策 |

首期决策请求必须显式传入唯一 `policyId`；不在多个启用策略之间隐式选择。显式策略的平台/分类作用域会进入冻结快照并在写入前执行：`null` 为通配，非空平台与候选运行精确匹配，非空分类要求候选运行不为空且全部案例分类一致，混合分类不得使用全运行级聚合指标冒充分类策略证据。未来如果增加自动命中，仍必须另行定义精确匹配、通配与多策略冲突优先级，不得依赖查询顺序。

### 9.5 治理总览

`GET /api/evaluation/overview` 的 `data` 只返回以下六个字段：

| 字段 | 口径 |
| --- | --- |
| `totalCases` | 全部评测案例数 |
| `reviewedCases` | `review_status = REVIEWED` 的案例数 |
| `frozenVersions` | 当前 `status = FROZEN` 的数据集版本数 |
| `runningRuns` | 仍需继续处理的 `QUEUED + RUNNING` 运行数 |
| `latestTerminalPassRate` | 最近终态运行的 `PASSED / (PASSED + FAILED) * 100`；无终态或无已确定结果时为 0 |
| `regressionCount` | 最近终态候选与最近完整可比基线之间的 `REGRESSED` 案例数；历史中不存在完整可比基线时为 0 |

最近终态运行固定按 `completed_at desc, id desc` 选择。基线候选必须来自同一 `platform_id`、同一冻结 `dataset_version_id`，并在选择阶段用双向集合差检查保证结果数、`case_id` 和 `snapshot_content_hash` 完全对齐，再按相同稳定顺序选最近一个真正可比的终态；紧邻但只有部分案例的 retry 会被跳过。回归分类与 Task 1 一致：通过转非通过或同成败类型下分数下降才是 `REGRESSED`；普通失败、执行错误和当前待人工复核均不计入。

总览不获得案例、数据集或运行域的可写仓储；`EvaluationOverviewService` 只依赖返回六个数字的 `EvaluationOverviewReader`。实现以一条参数不可控、不选取任何案例正文/输出/轨迹/凭据的固定 SQL 在同一语句快照中完成所有选择、对齐和聚合，服务边界仍标记只读 `REPEATABLE_READ`。它不调用 `EvaluationExperimentService.compare`，因此不会给 Task 1 的代理事务增加外层事务或弱化原有比较约束。

所有写接口必须进行状态校验；资源不存在返回 404，非法状态转换返回 409，参数错误返回 400，外部执行失败记录到结果而不是让整个批次直接丢失。

## 10. 评测器设计

首期评测器实现统一接口：

```text
EvaluationOutcome evaluate(EvaluationCaseSnapshot case, TargetExecution output)
```

首期提供：

| 类型 | 行为 |
| --- | --- |
| `EXACT` | 规范化空白后精确匹配 |
| `CONTAINS_ALL` | 必须包含全部期望片段 |
| `JSON_VALID` | 输出必须是合法 JSON，可选校验必需字段 |
| `NUMERIC_RANGE` | 从指定字段或正则提取数字并校验区间 |
| `FORBIDDEN_TERMS` | 不得出现敏感或禁止内容 |
| `MANUAL` | 自动执行但等待人工评分，不自动通过门禁 |

评分器必须确定性、无网络依赖且可单元测试。LLM Judge 作为后续阶段新增评分器，并要求保存评分 Prompt 版本、Judge 模型和原始理由。

## 11. 执行与一致性策略

### 11.1 快照

创建运行时一次性保存：

- 数据集版本与案例内容哈希。
- 模型 ID、模型名称和 Base URL；API Key 不进入快照。
- Prompt ID、版本名称、正文副本和正文哈希。
- 温度、最大 Token、超时和目标平台版本。

每次即将发起外部模型调用时，才按快照中的模型 ID 读取当前凭据，凭据不持久化也不写入运行内存快照。即使管理员随后修改模型或 Prompt 配置，本次运行仍使用已保存的端点、模型、Prompt 和参数快照；凭据轮换会影响同一运行中尚未发出的后续案例，以及恢复后尚未发出的案例。

### 11.2 持久化任务

- 创建任务先写入 `QUEUED`，事务提交后触发执行。
- 服务重启时扫描长时间停留在 `QUEUED/RUNNING` 的任务；`QUEUED` 可恢复，失联的 `RUNNING` 标为 `FAILED` 并保留原因。
- 执行并发由中台配置限制，默认单任务内串行，避免击穿模型限额。
- 单案例网络瞬时失败最多重试 2 次；4xx、无效配置和评分失败不盲目重试。

### 11.3 部分失败

一个案例失败不终止整个批次。全部案例结束后：

- 无执行错误为 `COMPLETED`。
- 部分案例为 `ERROR` 时为 `PARTIAL`。
- 任务级配置或快照不可用、没有任何案例执行时为 `FAILED`。

### 11.4 数据库运行边界

- 当前生产支持基线固定为 PostgreSQL，事务隔离使用 PostgreSQL 默认 `READ_COMMITTED`。
- P1 并发幂等导入依赖 PostgreSQL `INSERT ... ON CONFLICT DO NOTHING` 及其冲突等待语义；H2 的 PostgreSQL 模式只用于快速开发回归，不代表新的生产数据库兼容承诺。
- 如需切换数据库方言或提高隔离级别，必须先增加对应真实数据库的并发、约束与日志脱敏测试，并评估序列化失败的有限重试策略。

## 12. 安全与合规

- 案例导入 API 只接受脱敏内容；来源系统保留原文及映射关系。
- 案例人工创建、编辑和导入共用入库前敏感数据检测，拦截手机号、身份证号、Bearer/JWT、Key、Token、密码、私钥和常见云访问密钥形态；错误响应不回显命中的原文。
- 输入、输出和轨迹在写日志前限制长度并掩码身份证、手机号、Token、Key 和密码形态。
- 并发幂等导入使用数据库原子冲突处理，不以唯一约束异常作为正常控制流；数据库驱动错误详情与 ORM/JDBC 参数绑定日志默认关闭，避免约束失败时带出案例正文或外部标识。
- `api_key`、平台 Token 和数据库连接不写入评测表、结果 JSON 或前端响应。
- 高风险医疗案例不得仅凭 LLM Judge 自动放行。
- 首期复用中台部署边界，不新增公网入口；企业级 RBAC 纳入中台统一治理项目，不在本模块内另建账户体系。
- 删除案例仅允许逻辑归档；已冻结数据集和历史结果不可物理删除。

## 13. 前端信息架构

顶级菜单新增“评测治理”，图标使用 `Gauge`，路径 `/evaluation`，系统菜单锁定但允许控制可见性。

页面内部包含：

1. **总览**：案例数量、冻结数据集、运行中任务、最近通过率和退化数量。
2. **案例中心**：筛选、创建、审核和查看来源证据。
3. **评测集**：数据集、版本、案例编排和冻结操作。
4. **评测任务**：创建任务、进度、结果和错误重试。
5. **实验对比**：基线与候选的改进/退化明细。
6. **发布门禁**：策略和历史决策。

首期 UI 优先可用性和可追溯性，不引入复杂可视化。趋势图只在存在不少于两个可比较运行后展示。

## 14. 测试策略与最终验收

### 14.1 后端测试

- API 类型与 URL 契约测试。
- 路由和锁定菜单测试。
- 数据集冻结前后的交互限制测试。

- 新旧运行对比计算使用纯函数并进行 Node 单元测试。
- 最终执行 `npm test` 和生产构建。

### 14.3 最终验收场景

最终版本至少通过以下端到端场景：

1. 创建并审核 3 个不同评测器类型的案例。
2. 创建数据集、添加案例、冻结 V1，并证明 V1 不可修改。
3. 使用中台模型与 Prompt 创建运行并得到逐题结果。
4. 模拟一个执行错误，任务以 `PARTIAL` 结束且其他结果保留。
5. 修改 Prompt 后创建候选运行，比较结果能列出改进与退化。
6. 高风险案例失败时门禁返回 `FAIL`。
7. `MANUAL` 案例未人工评分时门禁返回 `REVIEW_REQUIRED`。
8. 前端能完成案例、数据集、运行、对比和门禁的主要操作。
9. 数据库、响应和日志均不出现测试 API Key 明文。
